WHAT THIS RUN PROVES
--------------------
1. The endpoint exists and matches the contract: multipart `file`, and the same
   {gaps, message} shape as POST /diagnostic/{id}/submit. No score.
2. It is a judgement, not a rubber stamp. Case C covered exactly the two
   prerequisites its syllabus teaches (class inheritance, virtual environments)
   and gapped the other six, in both .txt and real-PDF form.
3. Gaps from an upload are indistinguishable downstream: GET /student/gaps
   lists them and GET /student/gaps/{id}/lesson taught one at 77% alignment
   with 5 citations. Only detected_from differs, and that is for the teacher.
4. A scanned syllabus -- a VALID PDF with no text layer, which is what a phone
   photo becomes -- is refused with no_text_found. This is the failure that
   matters most: read as "a syllabus covering nothing", it would have returned
   a maximal 8-gap list built from zero evidence and looked like a real result.
5. A .docx is refused by its bytes, and a text file named .pdf still reads.
   The extension is never consulted.

THE BUG THIS RUN FOUND
----------------------
Case C failed on the first attempt with 400 unsupported_type. `_plain_text()`
was gating on the file extension, so a plain-text syllabus named `.pdf` was
rejected -- directly contradicting the promise in `extract_text`'s own
docstring that byte-sniffing makes the extension irrelevant. The extension
check was there to reject .docx; that is a property of the bytes, so it is now
done by measuring the ratio of printable characters after decoding. latin-1
decodes any byte sequence, so "it decoded" was never evidence that the upload
was text.
