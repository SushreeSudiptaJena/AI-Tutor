==============================================================================
A BUG THIS RUN FOUND: the request language was used as the translation SOURCE
==============================================================================
The run above shows en=88% and hi=87% with different top similarities. Chasing
that turned up something worse than a rounding difference.

`language` on a request means "the language I want to read in". The code passed
it as the *source* language of the inbound translation. So an English question
sent with language=hi was translated as though it were Hindi -- which is not a
no-op: Sarvam dutifully rewords it, the reworded text is what gets embedded,
and it retrieves different passages.

Measured before the fix: the SAME English question scored 88% with
language=en and 82% with language=hi, with DIFFERENT citations. A student who
switched the UI to Hindi got worse retrieval on the identical question.

Inbound translation now always uses auto-detection. A student who picks Hindi
and types an English question is ordinary, not an error.

WHAT THIS RUN PROVES
--------------------
1. A question asked in Hindi is answered in Hindi (Devanagari verified in the
   body, not just claimed by a field).
2. Citations are IDENTICAL to the English run and still name the English
   source book and page -- Django 5 By Example, pp. 108/99/107/95. They are
   produced by retrieval, which never sees the student's language.
3. The alignment score does not drift with the ANSWER's language: the same
   English question scored 88% / top_sim 0.8238 whether answered in English or
   in Hindi, with byte-identical `evidence` and `citations`. The score is
   computed on English text before anything is translated out.
4. A genuinely Hindi question scored 88% too -- the same as its English
   equivalent, citing the same pages. What can still move it by a point is
   that a Hindi question round-trips to a slightly different English sentence
   ("What is Django QuerySet and when do you evaluate it?"), so it embeds
   slightly differently. That is a property of the question actually asked,
   not of the language it is read in.
5. Gap lessons translate too, and score IDENTICALLY across languages -- the
   concept name comes from the database in English on both paths, so nothing
   is translated inbound at all.
6. With no ?language= and no body field, both /tutor/ask and the gap lesson
   fall back to the student's saved preferred_language. Before this, the
   preference existed and did nothing unless the frontend remembered to append
   a query parameter.
7. The reported `language` is what was PRODUCED, not what was requested.
   translate() returns its input unchanged when a call fails, so labelling
   English prose "hi" would tell a student the system answered in their
   language when it had not.

CHUNKING
--------
Sarvam's endpoint takes about a thousand characters; a gap lesson runs to two
or three thousand. Text is split on paragraph and then sentence boundaries
before it goes out and reassembled after. Without this the tail is silently
dropped -- and since a failed translation returns the input unchanged, that
failure is indistinguishable from "this text was already English".
