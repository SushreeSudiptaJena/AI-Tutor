TITLE: Foreign key placement in one-to-many relationships

BODY:
 First, acknowledge the intuition that the author “owns” the posts, so it feels natural to put a reference on the author side; that expectation is why many students adopt the opposite model. Second, point out the concrete failure: a single column on the author table could only store one post ID, so an author with two posts would have no place to record the second reference. The course material shows the opposite – Django creates an author_id column on the blog_post table (page 83) and the Comment model stores a post foreign key on each comment (page 177), exactly because the many side holds the key. Finally, reinforce the correct model: define the foreign key in the “many” model (Post) as models.ForeignKey(User, on_delete=models.CASCADE); this generates the foreign‑key column on the many‑side table, allowing any number of posts to point to the same author. teacher-005 -- THE BUG THIS RUN FOUND, AND THE FIX
==============================================================================
The run above ends with before/after reporting delta_share -0.3462 seconds
after the reteach was approved. That is the panel lying by arithmetic: zero
confirmations in the "after" window divides into a share of zero, which
subtracts into a triumphant negative delta -- while what actually happened is
that nobody had been asked yet. Zero evidence and zero occurrences are not the
same measurement, and the panel could not tell them apart.

Fixed by counting attempts on that problem_type inside the window. Verified
both states:

Found during verification: `GET /student/assignments` was in the frozen
contract and had never been built, so an approved reteach unit went nowhere.
The approval gate is only a human-in-the-loop story if approval leads
somewhere; until this existed the gate opened onto a wall. Built and verified.

Also found: the 422 refusal branch in suggest_reteach read `report`, which is
only bound on the SUCCESS path, so an honest refusal raised UnboundLocalError
and became a 500. Fixed to read exc.report. The branch is not rare -- it fired
on the second misconception tried.

WHAT THE STUDENT HALF PROVES
----------------------------
- A misconception the corpus cannot teach against is REFUSED at 43% alignment,
  with no unit drafted. Writing one anyway would put invented content behind a
  teacher's name the moment they approved it.
- A draft is invisible to the student it was written about. The rule is in the
  query (status == "assigned"), so a draft is never fetched rather than being
  fetched and filtered.
- Approving it makes it appear, with assigned_at read from the same audit row
  teacher-005 uses for its before/after boundary -- so the two panels cannot
  disagree about when a reteach happened.
- The payload names no misconception, no diagnosis, no confirmed count. The
  student is being taught the thing, not told a machine decided they believe
  the wrong version of it.
- citations[] is empty by design: a unit's citations are gathered while it is
  drafted and reteach_units has no column to keep them in. An empty list is
  honest; inventing sources at read time would not be.
